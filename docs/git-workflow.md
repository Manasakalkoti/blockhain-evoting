# Git Workflow

## Branch Strategy

```
main            ← stable, deployable state
  └── feature/TASK-XXX-short-description
  └── fix/short-description
  └── chore/short-description
```

- `main` is the integration branch. Direct commits to `main` are allowed during early development.
- Prefix branches with `feature/`, `fix/`, or `chore/` followed by the task ID from `EXECUTION_PLAN.md`.

## Commit Message Format

```
<type>(<scope>): <short summary>

[optional body — explain the *why*, not the *what*]
```

**Types:** `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `style`

**Scopes:** `auth`, `models`, `elections`, `contracts`, `workers`, `frontend`, `deps`, `ci`

### Examples

```
feat(models): add constituency and candidate tables
fix(auth): handle expired Firebase tokens gracefully
chore(deps): pin flask-limiter to 3.x
docs(git): add git workflow guide
```

Keep the summary line under 72 characters. Use the body to explain motivation or tradeoffs when the change isn't self-evident.

## Typical Development Flow

```bash
# 1. Start from an up-to-date main
git checkout main
git pull origin main

# 2. Create a task branch
git checkout -b feature/TASK-005-voter-registration

# 3. Make changes, then stage and commit
git add backend/app/api/auth.py backend/app/models/user.py
git commit -m "feat(auth): add voter registration endpoint"

# 4. Push and open a PR (or merge directly during solo dev)
git push -u origin feature/TASK-005-voter-registration
gh pr create --fill
```

## Staging Selectively

Avoid `git add .` or `git add -A` — these can accidentally stage `.env` files or large binaries.

```bash
# Stage specific files
git add backend/app/models/election.py

# Stage hunks interactively
git add -p backend/app/api/health.py

# Review what is staged before committing
git diff --staged
```

## Flask-Migrate (Database Migrations)

Migration files live in `backend/migrations/` and **must be committed**. They are the authoritative record of schema evolution.

```bash
cd backend

# After editing a model, generate a migration
flask db migrate -m "add wallet_address to users"

# Review the generated migration before applying
# (edit if auto-generated logic is wrong)

# Apply the migration
flask db upgrade

# Stage and commit the new migration file
git add migrations/
git commit -m "chore(models): add wallet_address migration"
```

> Never delete or manually edit migration files that have already been applied to shared environments.

## Tagging Releases

```bash
# Tag a milestone (e.g. after TASK-009 contract deployment is stable)
git tag -a v0.1.0 -m "MVP: auth + elections + contract deployment"
git push origin v0.1.0
```

## Common Fixes

### Undo last commit (keep changes staged)
```bash
git reset --soft HEAD~1
```

### Discard unstaged changes to a file
```bash
git restore backend/app/api/health.py
```

### Amend the last commit message (before pushing)
```bash
git commit --amend -m "fix(models): correct FK reference in VoteTransaction"
```

### Rebase feature branch onto latest main
```bash
git fetch origin
git rebase origin/main
```

## What NOT to Commit

- `.env` — contains secrets; use `.env.example` for templates
- `venv/` / `node_modules/` — reproducible via `pip install` / `npm install`
- `backend/instance/` — SQLite dev databases
- `contracts/artifacts/` / `contracts/cache/` — Hardhat build outputs (regenerated by `npx hardhat compile`)

These are all covered by `.gitignore` at the repo root and in `backend/` / `frontend/`.
